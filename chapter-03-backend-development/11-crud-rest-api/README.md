## 1. Learning outcomes and REST concepts

After this guide you should be able to explain what a REST resource is, build a JSON CRUD route, map each HTTP method to a database operation, test responses and status codes, filter and sort collections, separate the route and service responsibilities, diagnose common failures, and reuse the same structure for another resource.

**CRUD** is the common lifecycle of stored data: **Create, Read, Update, Delete**. A REST API exposes a **resource** (here a blog post) through stable HTTP URLs. URLs identify resources; HTTP verbs specify actions. Our API uses the prefix `/api/v1` to identify API version 1.

```text
PowerShell / Postman / React frontend
                 | JSON over HTTP
                 v
           Express application
             src/app.js
                 |
         src/routes/posts.js
         methods, URLs, statuses
                 |
         src/services/posts.js
           CRUD and queries
                 |
       src/db/models/post.js
        Mongoose validation
                 |
     MongoDB database: blog
     collection: posts (Mongoose default pluralization)
```

The source uses **Express 5**, **Mongoose 8**, `dotenv`, and JavaScript ES modules (`"type": "module"`). The app calls `express.json()` so JSON request bodies become `req.body`. The service layer uses Mongoose's `Post` model to query MongoDB.

### Read the resource representation

The actual `postSchema` has these fields:

| Field | Type | Source requirement |
| --- | --- | --- |
| `title` | `String` | Required |
| `author` | `String` | Optional |
| `contents` | `String` | Optional |
| `tags` | `String[]` | Optional list of tags |
| `_id` | MongoDB `ObjectId` | Generated by MongoDB/Mongoose |
| `createdAt`, `updatedAt` | `Date` | Managed via `timestamps: true` |

Sample valid **request body** (do not provide `_id` or timestamps):

```json
{
  "title": "My first Blog API post",
  "author": "Amina",
  "contents": "CRUD with Express and Mongoose.",
  "tags": ["nodejs", "express"]
}
```

A successful create response contains the persisted object with `_id`, timestamps and a Mongoose version field (normally `__v`). Field ordering is not part of the API contract.

## 2. Prerequisites and installation from zero

### 2.1 Install development tools (Windows)

1. Install a supported [Node.js LTS](https://nodejs.org/en/download) using the Windows installer (includes npm).
2. Install [Git for Windows](https://git-scm.com/install/windows) and [Visual Studio Code](https://code.visualstudio.com/download).
3. Install [MongoDB Community Server](https://www.mongodb.com/try/download/community) and [MongoDB Shell](https://www.mongodb.com/try/download/shell). The installer may offer a Windows service; leave its port at `27017` unless you have a reason to change it.
4. Restart the terminal, open PowerShell, and verify:

```powershell
node --version
npm.cmd --version
git --version
mongosh --version
Get-Service *MongoDB*
Test-NetConnection 127.0.0.1 -Port 27017
```

**Expected:** Version numbers print. If using the default MongoDB installation, the service is running and `TcpTestSucceeded` is `True`. `mongosh` can be installed separately; missing `mongosh` does not necessarily mean the server is missing. On some Windows installations, PowerShell blocks the `npm.ps1` shim: use **`npm.cmd`**, not a system-wide policy change.

**Alternative:** A MongoDB Atlas cluster also works if its user, IP access, TLS URI and credentials are configured correctly. Keep connection secrets out of Git.

### 2.2 Clone the actual Chapter 3

```powershell
New-Item -ItemType Directory -Force -Path "$HOME\Projects"
Set-Location "$HOME\Projects"
git clone https://github.com/XMAN-MHD/from-zero-to-fullstack-ch3-backend-development.git
Set-Location .\from-zero-to-fullstack-ch3-backend-development
npm.cmd ci
code .
```

**Expected:** npm installs the project from `package-lock.json`, and the root contains `src/`, `package.json` and `jest.config.json`. `npm ci` is appropriate for the checked-in lockfile; use `npm install` only when intentionally changing dependencies. The repository's npm scripts are `dev`, `start`, `lint`, `lint:fix` and `test`.

### 2.3 Configure the database port safely

The original connection file `src/db/init.js` contains:

```javascript
const DATABASE_URL =
  process.env.DATABASE_URL || 'mongodb://localhost:27018/blog'
```

If MongoDB is at its standard port **27017**, create an untracked file `.env` **at the repository root**:

```dotenv
DATABASE_URL=mongodb://127.0.0.1:27017/blog
PORT=3000
```

If you deliberately run MongoDB at **27018**, use `DATABASE_URL=mongodb://127.0.0.1:27018/blog`. Do not assume a port is correct: check `Test-NetConnection 127.0.0.1 -Port 27017` or port `27018` as appropriate. `src/index.js` calls `dotenv.config()` before database initialization; the source `.gitignore` excludes `.env`.

> **Safety:** The existing `initDatabase()` logs `DATABASE_URL` on successful connection. Avoid putting production credentials in logs; a future hardening change should log a safe success message instead. For this learning exercise, a credential-free local URI is easiest.

### 2.4 Start and verify the API

From the repository root:

```powershell
npm.cmd run dev
```

**Expected:** Once MongoDB is available, a database connection message and `express server running on http://localhost:3000` appear. Keep this terminal open. In another PowerShell window:

```powershell
Invoke-RestMethod -Method Get -Uri 'http://localhost:3000/api/v1/posts'
```

**Expected:** A JSON array (possibly `[]` if the database has no posts). A browser may also open this GET endpoint. If you get `ECONNREFUSED`, inspect MongoDB, `.env`, server terminal and occupied ports. If server startup fails, do not proceed to the CRUD exercises until it succeeds.

## 3. Read the actual source before changing anything

### 3.1 Express wiring: `src/app.js`

```javascript
import express from 'express'
import { postsRoutes } from './routes/posts.js'

const app = express()
app.use(express.json())
postsRoutes(app)
export { app }
```

`express.json()` parses JSON bodies when clients send `Content-Type: application/json`. `postsRoutes(app)` registers the paths and methods. A separate `src/index.js` loads `.env`, awaits `initDatabase()`, and then calls `app.listen(PORT)`. This ordering avoids starting the HTTP server before the initial database connection is established.

### 3.2 Data model: `src/db/models/post.js`

```javascript
import mongoose, { Schema } from 'mongoose'

const postSchema = new Schema(
  {
    title: { type: String, required: true },
    author: String,
    contents: String,
    tags: [String],
  },
  { timestamps: true },
)

export const Post = mongoose.model('post', postSchema)
```

The schema validates the existence of `title` on a document save; it does **not** automatically convert every bad HTTP request into `400 Bad Request`. The **HTTP layer must intentionally map** validation errors to an appropriate status; our current creation route catches them as `500`.

### 3.3 Separate responsibilities

| Layer | Actual file | Responsibility |
| --- | --- | --- |
| HTTP routing | `src/routes/posts.js` | Extract inputs, choose service call, send status and JSON |
| Business/data access | `src/services/posts.js` | Build queries, create/save/update/delete with `Post` |
| Data rules | `src/db/models/post.js` | Post schema, required title, timestamps |
| Database setup | `src/db/init.js` | Connect to MongoDB |
| Bootstrap | `src/index.js` | Read environment, await database, start listening |

This separation lets another interface reuse the service functions without duplicating Mongoose queries.

## 4. CREATE — `POST /api/v1/posts`

In the original route:

```javascript
app.post('/api/v1/posts', async (req, res) => {
  try {
    const post = await createPost(req.body)
    return res.status(201).json(post)
  } catch (err) {
    console.error('error creating post', err)
    return res.status(500).end()
  }
})
```

The original service creates a model instance and saves it:

```javascript
export async function createPost({ title, author, contents, tags }) {
  const post = new Post({ title, author, contents, tags })
  return await post.save()
}
```

**Try it in PowerShell** in the second terminal:

```powershell
$base = 'http://localhost:3000/api/v1/posts'
$body = @{
  title = 'My first Blog API post'
  author = 'Amina'
  contents = 'Create a post with REST'
  tags = @('nodejs', 'express')
} | ConvertTo-Json

$created = Invoke-RestMethod -Method Post -Uri $base `
  -ContentType 'application/json' -Body $body
$created | Format-List
$id = $created._id
Write-Host "Created post ID: $id"
```

**Expected:** A created post; the server returns status `201` and JSON, with an `_id` value. Save the ID in `$id` for GET, PATCH and DELETE. In Windows PowerShell, a trailing backtick (`` ` ``) continues the command on the next line; **do not add a space after it**. You can also write the command on one line.

**Important limitation in the actual source:** A missing `title` causes a Mongoose validation error; the route currently returns `500`, **not `400`**. The same route does not explicitly validate that the body is an object. Section 10 shows recommended improvements, not current repository behavior.

## 5. READ — collection and one post

### 5.1 List all posts

The route selects `listAllPosts(options)` when no `author` or `tag` filter exists; the service runs `Post.find(query).sort(sort)`.

```powershell
$allPosts = Invoke-RestMethod -Method Get -Uri $base
$allPosts | Select-Object _id, title, author, createdAt
```

**Expected:** A JSON array containing the post created in section 4. An empty collection yields `[]`. The default sort from the service is `createdAt` descending.

### 5.2 Read a single post

```powershell
$onePost = Invoke-RestMethod -Method Get -Uri "$base/$id"
$onePost | Format-List
```

The route passes `req.params.id` to `getPostById(id)` (which calls `Post.findById(id)`). If no document matches a valid, well-formed ObjectId, it returns **`404` with an empty body**. An invalid identifier (e.g. `not-an-id`) produces a Mongoose cast error and is currently caught as **`500`**. A recommended hardening is to validate the ID first and return `400` for malformed IDs.

## 6. UPDATE — `PATCH /api/v1/posts/:id`

The route passes the URL ID and `req.body` to `updatePost()`, returns `200` with the modified document or `404` if none matches. Our service uses an explicit allowlist, so unwanted fields such as `_id` and `createdAt` are not copied:

```javascript
export async function updatePost(postId, updates) {
  const updatedFields = {}
  for (const key of ['title', 'author', 'contents', 'tags']) {
    if (updates[key] !== undefined) {
      updatedFields[key] = updates[key]
    }
  }
  return await Post.findOneAndUpdate(
    { _id: postId },
    { $set: updatedFields },
    { new: true, runValidators: true },
  )
}
```

`new: true` requests the updated document; `runValidators: true` enables Mongoose update validators for the update operation. This is useful but is not a complete substitute for explicit HTTP input validation, especially for a partial update.

```powershell
$changes = @{ title = 'My updated Blog API post'; tags = @('api', 'crud') } |
  ConvertTo-Json
$updated = Invoke-RestMethod -Method Patch -Uri "$base/$id" `
  -ContentType 'application/json' -Body $changes
$updated | Select-Object _id, title, tags, updatedAt
```

**Expected:** `200 OK`, a changed `title` and tags. The existing author/content values remain. `updatedAt` reflects the modification. The original code uses `PATCH` (partial update), **not `PUT`**.

## 7. DELETE — `DELETE /api/v1/posts/:id`

The service calls `Post.deleteOne({ _id: postId })`. The route returns `404` when `deletedCount === 0`, otherwise **`204 No Content`**:

```powershell
Invoke-WebRequest -Method Delete -Uri "$base/$id" |
  Select-Object StatusCode, StatusDescription
```

**Expected:** HTTP `204`; the response body is empty by design. A subsequent GET for the deleted, formerly valid ID returns `404`. Because the ID is reused, do this section **last** after GET and PATCH.

**Repeat DELETE:** The route returns `404` on a second delete for the same ID. Do not expect a second `204` from the current source.

## 8. Filtering and sorting real Blog posts

The current list endpoint supports the following query string keys:

| Query parameter | Example | Actual behavior |
| --- | --- | --- |
| `author` | `?author=Amina` | Exact match on stored `author` |
| `tag` | `?tag=nodejs` | Posts whose `tags` array contains this value |
| `sortBy` | `?sortBy=title` | Field selected by caller; default `createdAt` |
| `sortOrder` | `?sortOrder=ascending` | Ascending only for exact `ascending`; otherwise descending |

**Try after creating at least two posts:**

In PowerShell, prefer the explicit `${base}` variable syntax before a `?` query string to make the variable boundary unambiguous:

```powershell
Invoke-RestMethod -Uri "${base}?author=Amina"
Invoke-RestMethod -Uri "${base}?tag=nodejs"
Invoke-RestMethod -Uri "${base}?sortBy=title&sortOrder=ascending"
Invoke-RestMethod -Uri "${base}?tag=nodejs&sortBy=createdAt&sortOrder=descending"
```

The original route deliberately **rejects `author` and `tag` together**:

```powershell
Invoke-WebRequest -Uri "${base}?author=Amina&tag=nodejs"
```

**Expected:** HTTP `400` with JSON `{ "error": "query by either author or tag, not both" }` (PowerShell may throw on a non-2xx response, see Section 9). Sorting and either one filter can be combined.

**Security and correctness caveat:** The original service creates `{ [sortBy]: sortValue }` from an unchecked client value. A production API should validate the allowed sort fields (`title`, `createdAt`, `updatedAt`, for example) and the permitted sort direction. Also limit result sizes and implement pagination for large collections.

## 9. Error handling, status codes and testing

### 9.1 Current behavior versus ideal API behavior

| Situation | Current Chapter 3 | Recommended improvement |
| --- | --- | --- |
| Valid create | `201` + JSON | Keep |
| Read existing ID | `200` + JSON | Keep |
| Missing valid ID | `404`, empty body | Consistent JSON error optional |
| Valid update | `200` + updated JSON | Keep |
| Successful delete | `204`, empty body | Keep |
| `author` and `tag` together | `400` + JSON | Keep or support combined search explicitly |
| Missing required `title` on create | `500`, empty body | `400` or `422` + safe validation details |
| Malformed ObjectId | `500`, empty body | `400` + validation message |
| Database unavailable on start | Startup connection error | Clear non-secret log + appropriate deployment health checks |
| Database operation exception | `500`, empty body | Generic JSON error without exposing internal details |

Do not treat a `500` for bad input as correct REST design just because it is what the **current source** does. This cheatsheet both teaches source reproduction and calls out behavior to improve later.

### 9.2 View response status in PowerShell

```powershell
# Success response including status and body
Invoke-WebRequest -Method Get -Uri $base |
  Select-Object StatusCode, Content

# An expected 404 can throw. Catch and inspect.
try {
  Invoke-WebRequest -Method Get -Uri "$base/000000000000000000000000"
} catch {
  Write-Host "HTTP request failed as expected: $($_.Exception.Message)"
  # In Windows PowerShell 5.1, the status may be on Exception.Response.StatusCode.
}
```

For easy visual testing, [Postman](https://www.postman.com/downloads/) or VS Code's REST Client extension can also send requests. When testing with `curl` on **Windows PowerShell 5.1**, `curl` may be an alias for `Invoke-WebRequest`; use `curl.exe` to invoke actual curl.

### 9.3 Test matrix for your checklist

| Test case | Request | Expected result from original API |
| --- | --- | --- |
| Empty database | `GET /api/v1/posts` | `200`, `[]` |
| Valid post | `POST /api/v1/posts` | `201`, new `_id` |
| Get new post | `GET /api/v1/posts/:id` | `200`, JSON object |
| Update title | `PATCH /api/v1/posts/:id` | `200`, updated JSON |
| Delete existing | `DELETE /api/v1/posts/:id` | `204`, no body |

| Missing title | `POST` with `{}` | Current source: `500`; improvement needed |
| Bad ID format | `GET /api/v1/posts/abc` | Current source: `500`; improvement needed |

```powershell

```

The Jest setup uses **MongoDB Memory Server**, which may download a MongoDB binary on the first run and therefore needs network access. These are **service/model-level tests** in the repository; do **not** assume they prove all HTTP routes and status codes. Our planned Cheatsheet 13 will cover automated testing more deeply.

## 10. Recommended hardening — NOT yet implemented in Chapter 3

These additions improve correctness and security. Keep them in a new branch or in a separate practice app; the source code described above stays the ground truth.

### 10.1 Validate incoming IDs and create payloads

```javascript
import mongoose from 'mongoose'

function isValidPostId(id) {
  return mongoose.isObjectIdOrHexString(id)
}

function validateCreatePost(body) {
  if (!body || typeof body !== 'object' || Array.isArray(body)) {
    return 'JSON object required'
  }
  if (typeof body.title !== 'string' || !body.title.trim()) {
    return 'title must be a non-empty string'
  }
  if (body.tags !== undefined &&
      (!Array.isArray(body.tags) ||
       !body.tags.every(tag => typeof tag === 'string'))) {
    return 'tags must be an array of strings'
  }
  return null
}
```

Use those checks **before** calling the service, then return `400` for invalid input. For a real application, consider a schema validation library for both body and query parameters. Explicitly decide whether whitespace-only strings, empty arrays and unknown keys are acceptable; `required: true` alone does not express the entire business contract.

### 10.2 Restrict sort keys and page results

```javascript
const allowedSortFields = new Set(['title', 'createdAt', 'updatedAt'])
const allowedOrders = new Set(['ascending', 'descending'])

function parseSort(query) {
  const sortBy = query.sortBy ?? 'createdAt'
  const sortOrder = query.sortOrder ?? 'descending'
  if (!allowedSortFields.has(sortBy) || !allowedOrders.has(sortOrder)) {
    return { error: 'Invalid sort option' }
  }
  return { sortBy, sortOrder }
}
```

For pagination, validate `page` and `limit` as bounded positive integers before building a database query. Always use deterministic sorting (for example a stable `_id` tiebreaker) for reliable page navigation.

### 10.3 Additional production safeguards

- Set size limits for JSON bodies (`express.json({ limit: '100kb' })` or an appropriate limit), and cap collection query results.
- Use centralized Express error handling to map Mongoose validation errors, cast errors and unknown failures consistently; avoid leaking database details in HTTP responses.
- Keep MongoDB credentials in environment variables or secret management, never in Git or exposed logs.
- Add authentication and authorization before exposing write endpoints publicly; our Chapter 3 Blog API currently does **not** implement them.
- Add CORS rules only when a separate frontend origin requires them; restrict allowed origins instead of indiscriminately allowing all.
- Protect the MongoDB instance through network controls, authentication and least privilege.
- For actual deployment, add monitoring, shutdown handling, rate limiting and automated HTTP integration tests appropriate to the threat model.

## 11. Troubleshooting on Windows

| Symptom | Likely explanation | Next action |
| --- | --- | --- |
| `npm.ps1 cannot be loaded` | PowerShell execution policy | Use `npm.cmd ci` / `npm.cmd run dev` |
| `Cannot find module` | Dependencies not installed or wrong directory | Go to cloned root; run `npm.cmd ci` |
| `ECONNREFUSED 127.0.0.1:27018` | MongoDB not listening on source's default port | Configure `.env` with your actual port (often `27017`) |
| `mongosh` not recognized | Shell not installed / PATH not refreshed | Install shell separately and reopen PowerShell |
| `404` on `/posts` | Wrong URL | Use `/api/v1/posts` |
| `500` on missing title | Source routes do not map validation errors | Correct payload; see recommended hardening |
| `500` on short ID | Mongoose cast failure | Use the real 24-character hex `_id`; see ID validation |
| `400` when filtering | Both `author` and `tag` provided | Supply only one filter |
| `EADDRINUSE` | Port 3000 is taken | Stop prior server or choose another `PORT` in `.env` |
| Tests cannot start MongoMemoryServer | Binary download blocked / incompatible runtime | Check network, supported binary version, Jest setup logs |
| `curl` behavior differs | PowerShell 5.1 `curl` alias | Use `curl.exe` or `Invoke-RestMethod` |

## 12. Quick reusable blueprint — adapt to a new resource

To create a new resource such as `products`, follow the same conceptual structure:

```text
src/
  app.js                 # register JSON parser and productsRoutes
  index.js               # bootstraps DB and starts HTTP
  db/
    init.js              # DB connection
    models/
      product.js         # Product schema
  services/
    products.js          # CRUD + business query rules
  routes/
    products.js          # HTTP methods, inputs and responses
```

| New resource task | Implementation decision |
| --- | --- |
| Identify fields | e.g. `name`, `price`, `stock`; document required fields |
| Model | `new Schema({ ... })` with explicit types and validators |
| Create | `POST /api/v1/products` returning `201` |
| List | `GET /api/v1/products` returning `200` and an array |
| Read one | `GET /api/v1/products/:id` returning `200` or `404` |
| Modify | `PATCH /api/v1/products/:id` with an update allowlist |
| Remove | `DELETE /api/v1/products/:id` returning `204` or `404` |
| Inputs | Validate body, params, filters, pagination and sort |
| Errors | Consistent `400`/`404`/`500` mapping |
| Verification | Test successful and failed requests |
| Security | Authentication, authorization, secrets and bounded queries |

### Reuse checklist

- [ ] Node.js, npm, Git and MongoDB installed; versions verified.
- [ ] `.env` configured with the correct `DATABASE_URL` and `PORT`; secrets ignored by Git.
- [ ] Source cloned; dependencies installed with `npm.cmd ci` from **root**.
- [ ] Server starts after successfully connecting to MongoDB.
- [ ] Every CRUD request is tested in the intended order; keep the created `_id`.
- [ ] Correct success codes: `201`, `200`, `200`, `200`, `204`.
- [ ] Filtering, sorting and the `author + tag` rejection checked.
- [ ] Missing resources, malformed IDs and missing required fields examined.
- [ ] Original limitations are not mistaken for best-practice behavior.
- [ ] Input validation, safe error responses, pagination and sort allowlist planned.
- [ ] Jest tests and linting run; outcomes recorded, not assumed.
- [ ] Guide and source changes committed separately with clear messages.
